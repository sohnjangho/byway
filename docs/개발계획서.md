## 1. 결론과 전체 순서

### 1-1. "프론트엔드 → 백엔드" 순서에 대한 판단

**맞다. 단, 세 조건이 붙는다.** 정확히는 **계약(코스 데이터 형식) → 프론트엔드 → 백엔드** 순서다.

| 근거 | 내용 | 출처 |
|---|---|---|
| PT 범위에서 서버가 필수인 기능은 하나다 | 부가 7 파티(실시간 위치)만 서버 없이 성립하지 않는다. 부가 1은 "저장"은 앱, "공유"만 서버다. 추가(코스 가져오기)·부가 2·4·5·8은 코스 데이터 파일과 앱만으로 된다(2장 표) | 기획서 3-3, 현재 코드 |
| 심사에 보이는 것은 앱 화면이다 | PT는 에뮬레이터 화면 시연이다. 현재 화면은 `MainActivity` 하나로, 코스 선택→미리보기→주행→정차 요약 흐름이 없다. 이것이 없으면 PT가 성립하지 않는다 | `app/src/main/java/com/byway/ui/MainActivity.kt` **[실측]** |
| 코스 데이터는 이미 서버 없이 들어간다 | 코스는 `app/src/main/assets/courses/*.json`에서 읽는다. 코스를 더 넣는 데 서버가 필요하지 않다 | `CourseFile.kt` **[실측]** |
| 서버 데이터 모델이 아직 없다 | 스팟·태그·테마·시간대가 코스 형식에 없다(`schemaVersion 1`은 path·sections만). 서버를 먼저 만들면 형식이 바뀔 때 두 번 고친다 | `Course.kt`, `CourseFile.kt` **[실측]** |
| 시연 장소 네트워크를 모른다 | 서버 의존을 PT 시점에 줄이는 것이 안전하다 | **[확인 필요]** |
| 1인 개발, PT까지 17일 | 두 축을 동시에 세울 여력이 없다 | 일정 |

**조건 세 가지**

| # | 조건 | 왜 |
|---|---|---|
| 1 | **코스 파일 형식 v2를 프론트엔드 단계 첫 작업으로 고정한다** (스팟·태그·테마·시간대·출처·작성자) | 이 형식이 곧 서버의 코스 테이블이다. 여기서 고정하면 서버는 같은 형식을 저장·전달만 한다. `core`가 순수 Kotlin이라 파서를 서버에서 그대로 쓸 수 있다 |
| 2 | **외부 API(TourAPI·기상청)는 PT 전에는 개발 머신의 오프라인 변환 도구로만 쓴다** | 제작가이드 10장 "API 키를 소스에 넣지 않는다. 외부 API는 자체 서버를 거친다". 서버가 없는 동안 차 안에서 외부 API를 부르면 규칙을 깬다. 코스 가져오기는 `tools/`에서 돌려 JSON으로 저장하면 된다 |
| 3 | **부가 7 파티는 PT 필수 범위에서 뺀다** (3장 범위 조정) | 서버가 있어야 하는 유일한 PT 항목이다. 넣으면 "프론트엔드 먼저"가 깨진다 |

**백엔드를 먼저 하는 순서가 틀린 이유:** 서버는 심사에 보이지 않고, 데이터 형식이 흔들리는 상태에서 만들면 다시 만들게 되며, PT 10일 전까지 화면이 없으면 시연이 없다.

## 3. 단계별 마일스톤

### 3-1. 범위 조정 [제안]

기획서 5-3(PT 전: 추가, 부가 2·4·5)과 5-4(PT 시연: 파티·서킷·저장 포함)가 서로 다르다. 5-3을 기준으로 맞추고 5-4를 아래처럼 고치기를 권고한다.

| 항목 | 5-4 현재 | 조정안 | 이유 |
|---|---|---|---|
| 코스 | 판교→두물머리 + 수도권 5개 | 판교→두물머리 + **3개 이상, 5개 목표** | 코스마다 충실도 측정(내비 거리 비교)과 코스 지점 검수가 필요하다. 첫 코스도 막다른 길 왕복을 고쳐 다시 만들었다 |
| 파티 | 서버 시뮬레이터로 재현 | **PT 이후**. 발표에서는 설계·화면 시안으로 설명 | 서버가 필요한 유일한 항목. 1-1 조건 3 |
| 서킷 | 용인 경계로 재현 | **후순위(P2)**. 경계 데이터가 있을 때만 | 데이터가 없고 지오펜스 정밀도 미검증 |
| 코스 저장·불러오기 | 포함 | 포함(로컬) | 서버 없이 됨 |
| 부가 2 | 미포함 | 포함(날씨 제외) | 코스가 여럿 생기면 목록 정렬에 바로 쓰인다 |

시연 코스 조건: 에뮬레이터 내비 위치가 판교 고정이므로 **주행 시연은 판교 출발 코스만** 가능하다. 다른 지역 코스는 목록·미리보기·목적지 제안으로만 보인다.

## 4. 레인 배정과 동시 작업

### 4-1. 1인 PM과 에이전트 개발의 규모

- 동시 레인은 **최대 3개**. 에뮬레이터가 1대라 `platform`·`tools` 계측은 한 번에 하나다. `core`·`feature` 시험은 에뮬레이터가 필요 없어 병렬이 된다.
- PM은 통합 담당이다. 레인 하나씩 병합하고 전체 시험을 돌린다. 하루 병합 1~2건이 현실적인 상한이다.
- 계약 변경은 하루 안에 작게 끝낸다. 계약 레인이 열려 있으면 다른 레인이 멈춘다.

### 4-2. 작업 묶음 → 레인

| 묶음 | 레인 | 소유 경로 | 선행 계약 | 동시 가능 |
|---|---|---|---|---|
| A 코스 형식 v2, 새 사건 | `contract` | `core/.../drive/`, `core/.../course/`, `docs/` | 없음(첫 작업) | 단독 |
| B 기어 어댑터, 코스 저장소, `DriveState` 확장 | `platform` | `app/.../platform/`, `app/.../service/` | A | C·D와 동시 |

### 5-2. 주행 중과 정차 중 구분

| 구분 | 판정 | 허용 | 금지 |
|---|---|---|---|
| 주행 중 | 기어 ≠ P | 한 줄 텍스트, 음성, 버튼 1개, 코스 그림(애니메이션 가능) | 목록·상세·편집·공유·광고·영상·자동 스크롤 |
| 정차 중 | 기어 = P | 모든 화면 | 없음 |

- 판정은 `DriveGate`가 `DrivingStateChanged(parked)`로 한다. 화면도 같은 값(`DriveState.parked`)으로 바뀐다. 두 곳이 다른 기준을 쓰지 않는다.
- 기어 전환 중 안전 기준은 "P가 아니면 주행"이다. 속도는 쓰지 않는다(FusedLocation에 속도 필드 없음 [실측]).
- 주행 중 Activity 유지는 `distractionOptimized` 선언으로 확인했다 [실측]. 정차 전용 화면을 별도 Activity로 둘지, 한 Activity 안에서 패널만 바꿀지는 **[확인 필요]**(Pleos가 주행 중 비선언 Activity를 어떻게 처리하는지). 안전한 쪽은 한 Activity + 패널 전환이다 **[권고]**.

### 6-2. 기술 선택 [권고]

| 항목 | 권고 | 이유 | 대안 |
|---|---|---|---|
| 언어·프레임워크 | **Kotlin + Ktor** | `core`가 순수 Kotlin이다. 코스 파서·구간 검증·geo 계산을 서버에서 import 한 줄로 그대로 쓴다. 코스 형식이 한 곳(`core/course`)에만 있게 된다. WebSocket 내장. 같은 저장소 `server/` 모듈로 두면 레인 도구가 그대로 적용된다 | Python FastAPI: PM 도구(`tools/*.py`)와 같은 언어지만 코스 파서를 두 번 만든다. BaaS(Supabase·Firebase): 가장 빠르지만 클라이언트 키를 앱에 넣는 구조라 "키를 앱에 넣지 않는다" 규칙과 충돌 소지 → 쓰려면 규칙 해석을 PM이 정해야 한다 |
| DB | **PostgreSQL** (관리형) | 위치 질의(반경 검색)는 PostGIS 없이도 바운딩 박스로 충분한 규모. 코스 JSON은 jsonb로 저장 | SQLite 파일: 초기엔 가능하지만 파티 동시 접속에서 바꾸게 된다 |
| 파티 채널 | WebSocket, 서버 메모리 + TTL | 위치는 저장하지 않는다. 종료·만료 시 사라진다 | Redis pub/sub: 인스턴스 1대면 불필요 |
| 호스팅 | 컨테이너 1대, 서울 또는 가까운 리전, HTTPS | 전시까지 사용자 수가 매우 적다 | **[확인 필요]** 실제 요금·리전 |
| 비밀 관리 | 환경 변수. 저장소에 `.env` 금지 | 가이드 10장 | — |

### 6-5. 인증 [권고]

- 차량 앱에 로그인 UX를 넣지 않는다. 최초 실행 시 서버가 **익명 디바이스 토큰**을 발급하고 앱 내부 저장소에 둔다.
- 파티는 **코드 기반**(6자리). 토큰은 남용 방지용이다.
- 코스 작성자 표시는 닉네임만. Pleos 계정 연동 API가 있는지 **[확인 필요]**(SDK 개요에 없음).

### 6-6. 개인정보

| 데이터 | 처리 |
|---|---|
| 파티 위치 | 서버 메모리만, TTL 60초, 파티 종료·만료 시 삭제. 동의 화면은 정차 중에만, 동의 버튼 외 행동은 동의로 보지 않는다(심사 기준) |
| 주행 궤적(부가 1) | 사용자가 "저장"을 누를 때만 로컬 저장, "공유"를 누를 때만 업로드. 자동 업로드 없음 |
| 완주 통계 | 디바이스 식별자 없이 저장 |
| 사진(부가 6 대체) | 사용자가 폰에서 직접 올린 것만. 번호판·얼굴 마스킹은 단계 3 후반 **[계획]** |
| 개인정보처리방침 | 앱 심사 필수. 앱 정보 화면과 모바일 웹에 링크 |

### 6-7. 배포·비용

- Docker 이미지 1개, 컨테이너 1대, 관리형 PostgreSQL 최저 플랜. 배포는 `main` 병합 시 수동 트리거(1인이라 자동 배포가 더 위험).
- 비용은 월 1~2만 원대를 가정한다 **[확인 필요: 호스트별 실제 요금]**. 전시 전까지 트래픽은 시연 수준이다.
- 앱에는 **서버 베이스 URL만** `BuildConfig`에 둔다. URL은 키가 아니다. TourAPI·기상청 키는 서버 환경 변수에만 있다. 병합 전 `grep -r "serviceKey\|apiKey"`가 0건이어야 한다.

### 6-8. 앱 쪽 연결 (단계 3 M)

- 코스 저장소에 원격 경로 추가. 자산·로컬·원격 세 경로가 되므로 `CourseSource` 인터페이스로 묶는다.
- 네트워크 실패는 코스 안내에 영향이 없어야 한다(가이드 6장). 원격 코스는 다운로드 후 로컬 저장소에 두고 주행은 로컬 파일로 한다.
- 파티는 `feature/party`가 `LocationUpdated`를 받아 `SendLocation` 명령을 내고, platform이 WebSocket으로 보낸다. 받은 위치는 `PartyMemberUpdated` 사건으로 들어온다.
