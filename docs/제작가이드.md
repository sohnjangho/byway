# 에움길 제작 가이드

이 문서는 코드보다 먼저 읽는다. 구조를 바꾸는 결정은 코드보다 이 문서를 먼저 고친다.

## 1. 목표

| 목표 | 뜻 | 확인 방법 |
|---|---|---|
| 유지보수가 쉽다 | SDK가 바뀌어도 고칠 파일이 정해져 있다. 코스 로직은 차 없이 시험한다 | SDK 타입은 `platform` 밖에 없다. `:core` 시험은 에뮬레이터 없이 돈다 |
| 부가 기능을 쉽게 붙인다 | 새 기능은 폴더 하나와 등록 한 줄이다. 핵심 코드를 고치지 않는다 | 부가 기능 PR의 diff에 `engine` 변경이 없다 |
| 부가 기능이 핵심을 망치지 않는다 | 부가 기능이 죽어도 코스 안내는 계속된다 | 시험으로 고정한다(6장) |
| 여러 에이전트가 동시에 개발한다 | 레인마다 고치는 경로가 겹치지 않는다. 계약만 지키면 서로 기다리지 않는다 | `tools/check-lane.sh`가 경로 침범을 잡는다(12장) |

## 2. 핵심 규칙 하나

> **사건이 들어오고, 명령이 나간다.**

코스 엔진과 모든 부가 기능은 같은 모양이다. 사건(`DriveEvent`)을 받아 명령(`DriveCommand`) 목록을 돌려준다. SDK를 직접 부르지 않는다. 명령을 실제로 실행하는 곳은 한 곳뿐이다.

```
 SDK 콜백(위치·기어·목적지)
        │  platform 이 DriveEvent 로 바꾼다
        ▼
   DriveHost ──▶ CourseEngine (핵심)
        │   └──▶ DriveFeature × N (부가 기능)
        │  모두 List<DriveCommand> 를 돌려준다
        ▼
   DriveGate  주행 규제 검사. 주행 중 금지 명령은 여기서 막는다
        ▼
   platform 이 SDK 호출로 실행한다
```

이렇게 하는 이유는 세 가지다.

1. 시험이 쉽다. 입력과 출력이 데이터라 가짜 객체 없이 값 비교로 끝난다.
2. 주행 규제가 한 곳에 모인다. 기능마다 규제를 다시 짜지 않는다.
3. 부가 기능끼리 서로 모른다. 하나를 지워도 다른 기능이 깨지지 않는다.

## 3. 프로젝트 구조

```
byway/
├─ core/                 순수 Kotlin 모듈. Android·Pleos 의존성 없음(컴파일러가 막는다)
│  └─ com.byway.core
│     ├─ geo/            GeoPoint, 거리, 경로 단순화
│     ├─ course/         Course, Section, Stop, 코스 파일 읽기
│     ├─ engine/         CourseEngine, LegPlanner, DriveTuning   ← 핵심 ①②③
│     └─ drive/          DriveEvent, DriveCommand, DriveFeature, DriveHost, DriveGate
├─ feature/              부가 기능. 기능 하나 = Gradle 모듈 하나. 폴더만 만들면 자동 포함된다
│  └─ ambience/          예: 부가 9 차 안 연출
├─ app/                  Android 모듈. 조립과 실행만 한다
│  └─ com.byway
│     ├─ platform/       Pleos SDK 어댑터. SDK 하나 = 파일 하나
│     │  ├─ PleosNavi.kt, PleosLocation.kt, PleosVoice.kt, PleosCabin.kt, PleosGear.kt, CarRestrictions.kt
│     ├─ service/        DriveService. 코스 주행을 소유한다
│     ├─ ui/             화면. 상태를 그리기만 한다
│     └─ FeatureRegistry.kt  부가 기능 목록. 켜고 끄는 유일한 곳
├─ server/               공유·파티 서버(Ktor + SQLite). core 를 그대로 가져다 쓴다. 앱은 서버 없이도 동작한다
└─ docs/                 이 가이드, 코스 파일 형식
```

`core`에는 위 넷 말고 `record/`(달린 길을 코스로 만드는 규칙)와 `share/`(앱과 서버가 함께 쓰는 공유·파티 자료형, 코드)가 있다.

**의존 방향은 한쪽뿐이다.** `app` → `feature` → `core`. `core`는 위를 모른다. `feature`는 `core`의 `drive`·`course`만 쓰고 `engine` 내부를 쓰지 않는다. 다른 `feature`를 쓰지 않는다. 모듈이 나뉘어 있어 기능끼리의 참조는 컴파일이 막는다.

**왜 `DriveService`인가.** 코스를 달리는 동안 화면 앞에는 차의 내비가 있고 에움길은 뒤로 간다. 주행 상태를 Activity가 가지면 화면이 바뀔 때 코스가 끊긴다. 그래서 서비스가 `DriveHost`를 소유하고 화면은 상태만 구독한다. 포그라운드 서비스 유형은 `specialUse`로 에뮬레이터 동작을 확인했다. 앱 마켓 심사 허용 여부는 **[확인 필요]**이다.

**스레드는 하나다.** SDK 콜백은 모두 메인 스레드로 넘겨 `DriveHost`에 넣는다. `core`에는 락을 두지 않는다.

## 4. 핵심 계약

```kotlin
sealed interface DriveEvent {
    data class CourseStarted(val course: Course, val resumeFrom: Int = 0) : DriveEvent
    data class LocationUpdated(val point: GeoPoint) : DriveEvent
    data class SectionEntered(val section: Section) : DriveEvent
    data class DrivingStateChanged(val parked: Boolean) : DriveEvent
    data object CourseFinished : DriveEvent
    data object RouteTakenOver : DriveEvent      // 운전자가 내비에 다른 목적지·경유지를 넣었다
    data object RouteCancelled : DriveEvent      // 운전자가 내비 안내를 껐다
    data object DestinationArrived : DriveEvent  // 운전자가 넣은 목적지에 닿았다
    data class Answered(val yes: Boolean) : DriveEvent
    data object CoursePaused : DriveEvent
    data object CourseStopped : DriveEvent       // 운전자가 코스를 끝냈다
}

sealed interface DriveCommand {
    data class FollowRoute(val leg: Leg, val path: List<GeoPoint>? = null) : DriveCommand
    data class Say(val text: String, val alert: Boolean = false) : DriveCommand
    data class ShowLine(val text: String) : DriveCommand
    data class ShowProgress(val sectionIndex: Int, val remainingMeters: Double) : DriveCommand
    data class Ask(val prompt: Prompt?) : DriveCommand   // 주행 화면의 답 버튼 하나. null 이면 거둔다
    data object RestoreCabin : DriveCommand
}

interface DriveFeature {
    val id: String
    fun onEvent(event: DriveEvent): List<DriveCommand>
}
```

- 사건과 명령은 필요할 때 추가한다. 쓰지 않는 사건을 미리 만들지 않는다.
- 엔진이 만든 사건(`SectionEntered` 등)은 호스트가 부가 기능에 다시 전달한다.
- 사건은 "일어난 일", 명령은 "해 달라는 일"이다. 이름도 그렇게 짓는다.

## 5. 부가 기능 추가 절차

순서대로 한다. 이 절차에서 벗어나야 한다면 기능을 만들기 전에 이 가이드를 먼저 고친다.

1. `feature/<이름>/` 폴더를 만들고 시험부터 쓴다. `build.gradle.kts`는 `feature/_template`을 복사한다. "이 사건이 오면 이 명령이 나온다"를 값으로 적는다.
2. 같은 폴더에 `DriveFeature` 구현을 쓴다.
3. 새 사건이나 명령이 필요하면 직접 고치지 않는다. 계약 레인에 먼저 요청한다(12장).
4. 화면이 필요하면 `app/.../ui/<이름>/`에 만든다. 주행 중에는 `ShowLine` 한 줄이 전부다.
5. `FeatureRegistry`에 한 줄 등록한다. 이 파일은 줄 단위로 자동 병합되므로 동시에 추가해도 충돌하지 않는다.

예시: 코스 구간에 들어서면 연출을 켠다.

```kotlin
class AmbienceFeature : DriveFeature {
    override val id = "ambience"
    override fun onEvent(event: DriveEvent) = when (event) {
        is DriveEvent.SectionEntered -> event.section.mood?.let { listOf(DriveCommand.SetCabin(it)) }.orEmpty()
        else -> emptyList()
    }
}
```

### 부가 기능별 연결표

| # | 기능 | 받는 사건 | 내보내는 명령 | 새로 필요한 것 |
|---|---|---|---|---|
| 1 | 코스 만들기 | 위치, 버튼 | 궤적 저장 | **`DriveFeature`가 아니다.** 코스 주행이 아니므로 `core/record` + `DriveService` 기록 상태 + `ui/record`로 둔다 |
| 2 | 테마·시간대 추천 | 주행 밖 | 코스 목록 정렬 | 코스 목록 화면 |
| 3 | 음악 연동 | `SectionEntered`, `CourseFinished` | `PlayMusic`, `StopMusic` | 연결된 음악 앱(`ConnectedMusic`) |
| 4 | 주변 코스 제안 | 목적지 변경 | `Say`, `ShowLine` | 목적지 사건 |
| 5 | 스팟 안내 | `LocationUpdated` | `Say`, `ShowLine` | 코스 파일의 스팟 |
| 6 | 풍경 사진 | 정차 | 사진 첨부 화면 | SDK 카메라 **[제안]** |
| 7 | 드라이빙 파티 | 위치, 파티원 위치 | 위치 전송, 지도 표시 | 서버. 2초 폴링은 `DriveService`가, 핀은 `SceneView`가 그린다. 사건·명령을 늘리지 않는다 |
| 8 | 서킷 랩타임 | `LocationUpdated` | `ShowLine` | 서킷 경계 데이터 |
| 9 | 차 안 연출 | `SectionEntered` | `SetCabin` | `PleosCabin` |

2번처럼 주행과 무관한 기능은 `DriveFeature`로 억지로 만들지 않는다. 코스 목록 쪽 기능으로 둔다. 코스를 가져오는 경로(추가 기능)도 두 번째 경로가 실제로 생길 때 공통 인터페이스를 뽑는다.

## 6. 안전장치

| 장치 | 규칙 |
|---|---|
| 주행 규제 | `DriveGate`가 판단한다. 판단식에 `else`를 두지 않아서 새 명령을 추가하면 컴파일이 멈춘다. 허용 여부를 정해야 빌드가 된다. 정차 판정은 기어가 P이고 `CarUxRestrictions`가 활성이 아닐 때만 참이다(`parkedFrom`). 규제 값을 얻지 못하면 기어로 판단한다 |
| 기능 격리 | `DriveHost`가 부가 기능을 하나씩 try/catch로 부른다. 예외가 나면 그 기능만 이번 주행에서 끄고 기록한다. `CourseEngine`은 항상 가장 먼저 호출한다 |
| 차종 차이 | `PleosCabin`이 Capability를 확인한다. 미지원 항목은 조용히 건너뛴다 |
| 외부 장애 | 네트워크 기능은 실패해도 코스 안내에 영향이 없어야 한다. 핵심 ①②③은 네트워크 없이 동작한다 |
| 광고 | 제휴 노출은 주행 중 어떤 명령으로도 나가지 못한다 |
| 운전자의 내비 경로 | 운전자가 내비를 직접 만지면(다른 목적지, 경유지 추가, 안내 종료) 코스는 멈추고 경로를 올리지 않는다. 끝낼 때는 우리가 올린 경로만 지운다(`RouteLedger`) |
| 연출 되돌리기 | 코스가 끝나거나 멈추면 연출이 바꾼 창문·풍량·조명을 처음 값으로 되돌린다. 운전자가 그 뒤 직접 바꾼 항목은 건드리지 않는다(`CabinMemory`) |
| 꺼짐 | 달리던 자리를 저장해 둔다. 앱이 꺼졌다 켜지면 정차 화면보다 먼저 이어갈지 묻는다(`SavedRun`, `Screen.Resume`) |

## 7. 코딩 규칙

- **시험 먼저.** `core`는 실패하는 시험을 먼저 쓴다. `./gradlew :core:test`로 에뮬레이터 없이 돈다.
- **SDK 타입 격리.** `ai.pleos.*` import는 `app/.../platform/`에만 있다. SDK가 바뀌면 이 폴더만 고친다.
- **숫자는 한곳에.** 이탈 판정 거리 같은 값은 `DriveTuning`에 둔다. 코드에 흩어 놓지 않는다.
- **안내 문구는 한곳에.** 엔진 음성 문구는 `engine/Messages.kt`에 둔다. 부가 기능 문구는 기능 폴더에 둔다.
- **브랜드명은 식별자에 쓰지 않는다.** 앱 이름은 `app_name` 한 곳이다. 클래스 이름에 Byway, 에움길을 넣지 않는다. 영문명이 바뀌어도 패키지 경로만 바꾸면 끝나야 한다.
- **코스 파일에는 `schemaVersion`을 둔다.** 저장된 코스가 앱 업데이트로 깨지지 않게 한다.
- **미리 만들지 않는다.** 인터페이스는 구현이 둘이 될 때 뽑는다. 예외는 `DriveFeature` 하나다. 구현이 아홉 개로 예정되어 있다.
- 한 파일이 한 가지 일을 한다. 300줄이 넘으면 나눌 때가 됐다는 신호다.

## 8. 시험 전략

| 대상 | 시험 | 실행 |
|---|---|---|
| `core` 전체 | JVM 단위 시험. 가짜 객체 없이 값 비교 | `./gradlew :core:test` |
| 부가 기능 | 사건을 넣고 명령을 비교 | `./gradlew :feature:<이름>:test` |
| `DriveGate`, 기능 격리 | 금지 명령 차단, 예외 기능 격리 | 위와 같음 |
| `platform` | 에뮬레이터 계측 시험 | `./gradlew connectedDebugAndroidTest` |
| 전체 시연 | 위치를 코스 위로 흘려 보내는 스크립트 | `tools/` |

**화면 배치 실측.** Pleos는 운전 정보 영역과 앱 영역을 나누고, 앱 영역은 앱 1개(가로) 또는 앱 2개(세로 각 841×1210)를 띄운다. 분할은 운전자가 창 막대를 끌어서 만들고, 창 막대를 누르면 두 칸이 바뀐다. 앱이 분할을 요청하는 방법은 없다(`LAUNCH_ADJACENT`도 무시된다). 분할 상태에서 코스를 시작하면 앱이 그대로 보이고 내비가 옆 칸에서 바로 안내한다. 전체 화면일 때는 내비가 앞으로 나와 앱을 가린다. 그래서 모든 화면은 841폭 세로에서도 맞아야 한다.

에뮬레이터 내비 위치는 판교 고정이다. 구간 교체 뒤 내비 화면의 출발점은 판교로 표시된다. 구간을 올리면 내비가 앞으로 나오고 경로 선택 화면이 뜬 뒤 자동으로 시작한다. 위치 판정은 `FusedLocation` 기준이다. 실차에서 달라지는 부분이므로 시연 때 이 한계를 숨기지 않는다.

## 9. 코스 데이터

- 코스는 `app/src/main/assets/courses/*.json`에 둔다.
- 코스는 도로 좌표열, 구간(이름·시작·끝·분위기), 스팟을 가진다.
- 판교→두물머리 도로 좌표는 OpenStreetMap 기반이다. 앱 정보 화면과 README에 ODbL 출처를 표시한다.
- 같은 도로를 되밟는 코스가 있다. 위치 판정은 진행 지점 앞쪽 일정 거리 안에서만 찾는다.
- 경유지는 적을수록 코스를 잘 따른다. 값을 바꾸면 `CourseFidelityTest`로 내비 계산 거리를 다시 잰다.
- 막다른 길 위에 코스 지점을 두지 않는다. 왕복 구간이 생긴다.

## 10. 저장소 규칙

- `main`에 직접 작업하지 않는다. `feature/<설명>` 브랜치, 변경마다 `~/reports` PR 보고서를 쓴다.
- **블라인드 심사.** 공개 저장소에 실명·이메일·소속을 넣지 않는다. 공개 전 커밋 작성자를 점검한다.
- **키 금지.** API 키를 소스에 넣지 않는다. 외부 API는 자체 서버를 거친다.
- **Pleos SDK 라이선스.** AAR을 디컴파일하거나 분석하지 않는다. API는 문서, 자동완성, 에뮬레이터 실측으로 확인한다.
- 스파이크 시험은 `platform` 시험이 대체하면 지운다.
- **`unregisterGearSelection`을 부르지 않는다.** 한 곳에서만 불러도 프로세스 전체의 기어 알림이 끊긴다. `PleosGear`는 알림과 별개로 2초마다 다시 읽는다.
- 로그는 `adb logcat -d`로 나중에 읽지 않는다. 이 에뮬레이터는 로그가 많아 앞줄이 사라진다. 측정 전에 `adb logcat -v time -s <태그>:I`로 받는다.

## 11. 만드는 순서

| 순서 | 내용 | 완료 기준 |
|---|---|---|
| 1 | `:core` 모듈 분리, `feature` 자동 포함, 레인 도구, geo·코스 파일 | `:core:test` 통과 |
| 2 | `LegPlanner`, `CourseEngine` | 구간 교체·이탈·복귀 시험 통과 |
| 3 | `DriveHost`, `DriveGate`, 기능 격리 | 6장 시험 통과. **여기서 계약 v1 확정** |
| 4 | `platform` 어댑터, `DriveService`, 주행 화면 (병렬 가능) | 에뮬레이터에서 코스 주행 |
| 5 | 시연 스크립트, 영상, APK, 저장소 공개 준비 | 11.15 제출본 |
| 6 | 부가 기능들 (기능별 병렬 가능). 첫 기능은 9 차 안 연출 | 5장 절차만으로 추가됨을 확인 |

## 12. 여러 에이전트 동시 개발

원칙은 하나다. **계약은 한 명이 순서대로 고치고, 나머지는 각자 경로 안에서 병렬로 일한다.**

### 레인과 소유 경로

| 레인 | 소유 경로 | 하는 일 |
|---|---|---|
| `contract` | `core/.../drive/`, `core/.../course/`, `settings.gradle.kts`, `docs/` | 사건·명령·게이트·코스 형식. **한 번에 한 에이전트만** |
| `engine` | `core/.../engine/`, `core/.../geo/` | 코스 변환, 구간, 이탈·복귀 |
| `platform` | `app/.../platform/`, `app/.../service/`, `AndroidManifest.xml` | SDK 어댑터, 서비스 |
| `ui` | `app/.../ui/` | 화면. `DriveState` 표본 값으로 혼자 개발한다 |
| `feature-<이름>` | `feature/<이름>/`, `app/.../ui/<이름>/` | 부가 기능 하나 |
| `tools` | `tools/`, `app/src/main/assets/courses/` | 시연 스크립트, 코스 데이터 |
| `server` | `server/` | 공유·파티 서버. 자료형은 `core/.../share/`(contract 레인)에서 받는다 |

`FeatureRegistry.kt`는 모든 `feature-*` 레인이 한 줄씩 추가할 수 있는 유일한 공유 파일이다. `.gitattributes`의 `merge=union`으로 자동 병합한다.

### 작업 규칙

1. **작업 공간을 나눈다.** 레인마다 git worktree 하나를 쓴다. 위치는 `../byway-wt/<레인>`, 브랜치는 `feature/<레인>-<설명>`이다. 빌드 폴더가 분리되어 서로 덮어쓰지 않는다.
2. **자기 경로만 고친다.** 병합 전 `tools/check-lane.sh <레인>`을 통과해야 한다. 다른 레인 파일을 고쳐야 한다면 고치지 말고 요청한다.
3. **계약 먼저.** 새 사건·명령이 필요하면 `contract` 레인이 작은 변경으로 먼저 병합한다. 그 뒤 필요한 레인이 최신 기준으로 다시 올라탄다. `contract` 변경에는 `DriveGate` 허용 여부를 함께 정한다.
4. **명령 실행은 뒤따른다.** 새 명령의 SDK 실행은 `platform` 레인이 맡는다. 실행이 아직 없으면 `platform`은 기록만 남기고 무시한다. 기능 레인은 기다리지 않는다.
5. **에뮬레이터는 하나다.** `tools/emulator-lock.sh`로 잠그고 쓴다. `core`와 `feature` 시험은 에뮬레이터가 필요 없으므로 병렬로 돈다.
6. **병합은 통합 담당 한 곳이다.** 레인 하나씩 병합하고 그때마다 전체 시험을 돌린다. PR 보고서 파일명에는 레인을 붙인다(`pr_YYYYMMDD_HHMM_<레인>.md`).

### 병렬 시점

| 단계 | 동시 작업 |
|---|---|
| 11장 1~3 | 병렬 없음. 계약이 없으면 병렬이 충돌만 만든다 |
| 11장 4 | `platform`, `ui`, `tools` 동시 |
| 11장 6 | `feature-*` 기능별 동시. 단 `contract` 요청은 순서대로 처리 |

### 에이전트 지시서 양식

```
레인: feature-spot
목표: 코스의 다음 스팟 1개를 주행 중 한 줄과 음성으로 안내한다
소유 경로: feature/spot/, app/.../ui/spot/
기준 계약: main 의 커밋 해시
완료 기준: ./gradlew :feature:spot:test 통과, tools/check-lane.sh feature-spot 통과
금지: core 수정, 다른 feature 참조, ai.pleos import
```

저장소 루트의 `CLAUDE.md`가 이 가이드를 가리킨다. 에이전트는 작업 전에 2·5·7·12장을 읽는다.

## 13. 디자인 값 고치는 법

디자인 값의 원본은 `design/tokens.json` 하나다. 색, 글자 크기, 간격, 버튼 치수를 바꿀 때는 이 파일만 고치고 도구를 돌린다.

```
python3 tools/make-theme.py
```

| 만들어지는 파일 | 쓰는 곳 |
|---|---|
| `app/.../ui/Palette.kt` | 앱. 주간·야간 색과 치수 |
| `design/screens/tokens.css` | 화면 시안 |
| `design/system/components/bundle.css` | 디자인 시스템 미리보기. 글자 클래스와 `app.css`를 묶은 것 |

- 만들어진 파일은 직접 고치지 않는다.
- 화면 코드와 시안에 색 값을 쓰지 않는다. 앱은 `Palette`, 시안은 `var(--이름)`만 읽는다.
- 공통 모양은 앱은 `ui/` 공통 조각, 시안은 `design/screens/app.css` 한 곳에 둔다.
- 시안은 야간 원본만 고치고 `python3 tools/make-day.py`로 주간판을 만든다. `*Day.dc.html`은 직접 고치지 않는다.
- 시안의 코스 값은 `design/screens/courses.js`다. 코스 파일이 바뀌면 `python3 tools/make-screen-data.py`를 돌린다.
- 앱은 시스템 주야 모드를 따른다. `Configuration.uiMode`가 바뀌면 지금 화면을 다시 그린다. 앱 안에 테마 선택을 두지 않는다.
- 주간 전용·야간 전용 규칙은 `.stage[data-theme="night"]`처럼 `.stage`에 묶어 쓴다. 디자인 시스템 미리보기 창은 `<html>`에 테마를 달아서 `[data-theme]`만 쓰면 다른 테마 칸까지 번진다.
- 지도 그림은 두 레이어다. 위성(`<id>.jpg`)과 일반 지도(`<id>-map.jpg`)를 `tools/make-covers.py`의 `LAYERS`가 정하고, 레이어마다 주간·야간(`-night`) 두 벌을 만든다. 커버, 장면, 한국 지도가 같은 이름 규칙을 쓴다. 앱은 설정의 지도 보기에 따라 고르고(`ui/MapStyle.kt`, `coverFile`), 일반 지도 그림이 없으면 위성으로 대신한다.
- 일반 지도의 야간판은 `night_map`이 만든다. 물은 앱 바탕색(`bg` 야간값)과 같게 해서 지도 가장자리가 보이지 않게 하고, 땅은 조금 밝게, 도로는 더 밝게 한다.
- 코스 커버의 구간 색도 `tokens.json`에서 읽는다. 야간판은 사진만 어둡게 하고 코스 선은 그대로 둔다.
- 흐린 사진 배경(`-soft.jpg`)은 없앴다. 글 칸은 바탕색이고 지도가 그 옆에서 시작한다. 경계 값은 `ui/SceneGeometry.kt`의 `sceneFade`, `photoFade` 한 곳이다.
- 풍경 사진은 `tools/scenery.json`에 이용 조건과 함께 적고 `tools/add-scenery.py`로 넣는다. 코스 파일의 `sceneryCredit`이 비어 있으면 앱이 사진을 보이지 않는다.
- 메인 바탕은 `tools/make-scenes.py`가 만든다. 위성 사진 위에 경로 칸을 잡고, 경로가 왼쪽 정보 칸과 겹치지 않게 맞춘다.
- 분위기 효과는 `tools/make-effects.py`가 `design/screens/effects.css`로 만든다. 지도와 경로는 건드리지 않는다.
- 앱의 위성 장면, 한국 지도, 경로 좌표, 효과 값은 `tools/make-app-scenes.py`가 시안과 같은 원본에서 `app/src/main/assets/scene`, `atlas`로 만든다. 시안 자료를 고치면 이 도구를 다시 돌린다.
- 앱 메뉴는 홈, 둘러보기, 랭킹, 내 코스 넷이고 맨 아래에 설정이 있다. 지도는 미리 만든 그림 위에 경로를 그리며 지도 라이브러리를 쓰지 않는다.
- 설정(`ui/SettingsScreen.kt`)에는 지도 보기, 달릴 때 켜고 끄는 것, 앱 정보, 내 기록 지우기를 둔다. 대화상자를 쓰지 않는다. 주야간 선택은 넣지 않는다.
- 고르는 조작은 운전석에서 가까운 왼쪽에 둔다. 글 칸과 목록, 지도 확대 단추, 풍경 버튼, 설정이 모두 창의 왼쪽이고 지도는 오른쪽이다.
- 코스 훑어보기는 `tools/make-frames.py`가 코스마다 사진 16장과 지점 자료를 만든다(`design/screens/images/frames`). 사진은 지금 위성 조각이고, 차량 카메라 사진이 생기면 같은 이름의 파일만 바꾼다. 화면은 `ui/ScrubStrip.kt`, 계산은 `ui/ScrubMath.kt`다. 띠는 언제나 지금 고른 코스이고, 다른 코스는 서랍(`ui/CourseDrawer.kt`, 계산 `ui/DrawerMath.kt`)에서 고른다.
- 코스 경로나 `tools/nearby.json`을 고치면 `make-screen-data.py` → `make-frames.py` → `make-app-scenes.py` 순서로 다시 돌린다. 훑어보기 사진은 파일이 있으면 다시 받지 않으므로, 경로를 바꾼 코스는 `design/screens/images/frames/<id>` 폴더를 지우고 돌린다. 훑어보기의 장소 번호는 도구가 매긴 번호이고 화면이 목록 번호로 바꾼다(`shownNumbers`).
- 홈의 숫자 칸은 거리, 계절 적합, 시간 적합, 운전 즐거움, 연료량이고 그 아래에 경치 한 줄을 둔다. 계산은 `core`의 `CourseFit.kt`다. 모두 예상값이고 화면에 그렇게 적는다.
  - 계절 적합: 추천 계절의 절정일(봄 4/10, 여름 7/20, 가을 10/25, 겨울 1/20) 앞뒤 20일은 100%이고 반년 떨어지면 20%다. 코스마다 사람이 고른 계절 하나에서 나온 추정이다.
  - 시간 적합: 날짜와 코스 출발 위치로 일출·일몰을 계산해, 지금 출발해 달리는 시간(가볍게 기준) 중 추천 시간대와 겹치는 비율이다.
  - 운전 즐거움: km당 커브 50, km당 오르내림 20, 돌아가는 정도 15, 도심 밖 비율 15로 낸 0~100점이다. 가중치는 제안값이고 사람의 평가가 아니다.
  - 연료량: 코스 거리 ÷ 차의 평균 연비(km/L)나 전비(km/kWh)다. 값을 못 읽거나 범위 밖이면 칸을 숨긴다. 에뮬레이터에서는 조회가 모두 실패해 실제 값으로 확인하지 못했고 단위도 실차 확인이 필요하다.
- 예상 소요 시간(가볍게, 쉬어 가며, 머물며)은 `core`의 `paceOf`가 코스 길이, 굽이 수, 코스 주변 정보의 종류에서 어림한다. 측정값이 아니므로 화면에 "예상"이라고 적는다.
- 2026-11-09의 화면 변경(일반 지도, 설정, 경계, 훑어보기, 소요 시간)은 `design/screens`의 HTML·CSS 원본에 아직 옮기지 않았다. 설계는 `docs/superpowers/specs/2026-11-09-design-refresh-design.md`다.
- 둘러보기·내 코스·랭킹의 한국 지도는 `tools/make-atlas.py`가 만든다. 이어서 `tools/make-screen-data.py`, `tools/make-day.py`를 돌린다.
- 분위기 판단은 `core`의 `moodFor(weather, hour, month)`다. 날씨, 시간대, 계절 순으로 본다. 날씨 입력은 아직 연결하지 않았다.
- 음성 안내는 `feature/guide`, 분위기 음악은 `feature/music`이다. 음악은 앱이 재생하지 않고 `platform/ConnectedMusic.kt`가 차에 연결된 음악 앱에 찾아 틀기를 요청한다. 켜고 끄는 값은 `MyDrives.musicOn`이다.
- 추천 표시의 낱말은 `ui/TagLabels.kt`의 `PICK_WORD` 하나다. 코스별 값은 `tools/courses/`의 `tags.seasons`, `tags.ages`다. 주행 통계가 생기면 이 값만 바꾼다.

## 14. 자율주행 연동

현대차그룹은 2028년 SDV 양산차에 고속도로 핸즈오프 수준의 L2+를 넣고, 2029년 자체 AI로 잇는다고 발표했다. 앱용 공개 SDK에는 아직 자율주행 API가 없다. 내부 문서에 `Adas` API가 있고 Pleos 디자인 파일에 자율주행 표시와 전용 색이 있다. 그래서 지금은 연결 지점만 만들어 둔다.

| 연결 지점 | 지금 | 자율주행이 열리면 |
|---|---|---|
| `RouteFollower` | 내장 내비가 경유지 2개씩 안내 | 자율주행 구현 하나를 `platform`에 더한다 |
| `RouteAbility` | `maxWaypoints = 2` | `acceptsWholePath = true`면 코스 좌표 전체를 한 번에 넘긴다. 구간 분할이 사라진다 |
| `DriveMode` | 항상 `MANUAL` | 차의 상태를 `DriveModeChanged` 사건으로 넣는다 |
| `DriveGate` | 정차 중에만 패널 허용 | `EYES_OFF`에서도 허용. 운전자가 되찾으면 즉시 닫는다 |

- **규제 기준은 손이 아니라 시선이다.** `HANDS_OFF`(L2+)는 도로를 봐야 하므로 규제를 풀지 않는다. 시선을 뗄 수 있는 `EYES_OFF`에서만 푼다.
- 코스의 원본은 경유지가 아니라 좌표 전체(`Course.path`)다. 경유지는 내비 제약 때문에 만든 파생값이다. 그래서 자율주행은 코스를 그대로 받는다.
- 코스 엔진, 부가 기능, 화면 규칙은 바꾸지 않는다. 새 구현과 값만 더한다.
- 자율주행 구현을 추측으로 미리 쓰지 않는다. API가 공개되면 그때 `platform` 레인이 만든다.

## 15. 주행 중 상태

주행 화면(`ui/DriveScreen.kt`)은 홈과 같이 지도 장면(`ui/SceneView.kt`)을 깔고 글 칸을 경계 없이 잇는다. 글 칸에는 코스 이름과 구간, 남은 거리, 구간 막대, 안내 문구, 앞으로 만날 곳, 코스 끝내기를 둔다. 글 칸 뒤에는 구간 색 위에 코스 사진을 흐리고 옅게 깐다(`ui/DriveBackdrop.kt`). 사진이 없는 코스는 구간 색만 쓰고, 불투명도는 사진이 가장 밝은 경우에도 글자 대비 4.5:1을 지키는 값이다. 지도에는 경로와 번호, 위치 점이 있고 설정의 지도 종류를 따른다. 스크롤과 애니메이션, 분위기 효과, 훑어보기 사진 띠는 정차 화면에만 있다. 위치 점은 남은 거리로 코스 위에 놓으므로 코스를 벗어나면 마지막 코스 위 자리에 머문다.

`CourseEngine`은 코스 하나를 달리는 동안 아래 상태를 오간다. 설계와 근거는 `docs/보완과제_실패사례_v01.md`다.

| 상태 | 들어오는 때 | 하는 일 |
|---|---|---|
| 접근 중 | 코스를 시작했고 아직 코스 위가 아닐 때 | 첫 위치에서 한 번 정한다. 출발점 근처면 그대로, 코스 중간이면 그 자리부터, 멀면 출발점을 첫 경유지로 올린다. 이탈을 알리거나 묻지 않는다. 코스에 닿기 전에는 구간을 알리지 않아 창문 연출과 음악이 켜지지 않는다 |
| 코스 위 | 위치가 허용 오차 안일 때 | 목적지 1km 전에 다음 경로를 올린다. 올리는 동안 안내가 7~8초 끊기므로(에뮬레이터 실측) 내비가 알려 준 다음 안내 지점이 500m 안이면 지나간 뒤로 미루고, 목적지 400m 전에는 미루지 않는다. 앞 경로의 목적지가 새 경로의 첫 경유지다 |
| 묻는 중 | 연속 세 번 벗어났을 때(그 구간에서 처음) | 경로를 바꾸지 않고 "잠깐 들르시나요?"를 묻는다. 답이 없으면 위치 15회 뒤 복귀 안내로 간다 |
| 코스 밖 | 들른다고 답했거나 복귀 경로를 올렸을 때 | 경로를 다시 올리지 않는다. 300m 안으로 두 번 연속 들어오거나 복귀 지점을 지나면 돌아온 것이다. 탐색 범위 밖에서 코스를 따라 300m 나아가거나 허용 오차 안에 30회 연속으로 있어도 돌아온 것이고, 이때는 남은 경로를 다시 올린다 |
| 멈춤 | 운전자가 내비를 직접 만졌을 때 | 경로를 올리지 않고 위치만 받는다. "코스 이어가기"를 누르면 남은 경로를 한 번 올린다 |

- 엔진은 시각을 모른다. 기다리는 시간은 위치 사건의 횟수로 센다(`DriveTuning.askWaitFixes`).
- 내비에 올리는 경로는 미리 자른 묶음이 아니라 "앞에 남은 지점"에서 그때그때 뽑는다(경유지 2개와 목적지 1개).
- 복귀 지점은 차 옆 자리에서 500m 앞의 코스 위 자리다. 가까이에 지점이 있으면 그 지점을 쓴다. 지점으로만 돌아오면 실제 코스에서는 5~15km를 건너뛴다.
- 같은 구간에서 두 번째 벗어나면 묻지 않고 지점을 하나 더해 복귀시키고, 세 번째면 그 구간은 내비에 맡긴다.
- 종점 300m 안에 세우면 끝까지 달린 것이다. 연속한 두 위치가 500m 넘게 떨어지면 위치가 끊겼던 것으로 보고 넓게 다시 맞춘다.
- 음성은 경로를 올린 직후 2.5초 미룬다(내비 안내와 겹치지 않게). 음성을 꺼 두어도 이탈·복귀·경로 교체는 알림음 하나를 낸다.
- 내비 이벤트는 SDK 문서와 실제가 다르다. 실측은 보완 과제 문서의 "내비 이벤트 실측"에 있다. `onDestinationChanged`는 오지 않고, 우리 요청에도 `onRouteCancelled`가 먼저 온다.
